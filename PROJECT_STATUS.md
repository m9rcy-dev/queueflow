- The existing `GET /public/codes/:code` resolver (Phase 4's join flow) now explicitly rejects a `DISPLAY` code with the same uniform 404 as an unknown/deactivated one — it only ever understands `QUEUE` codes. A `DISPLAY` code is resolved by a new, separate endpoint instead, since the board needs a live feed, not a one-shot lookup (matches the plan's own original split into two distinct routes).
- New `GET /public/displays/:code/events` (SSE, `DisplaysModule`) — mirrors Phase 4's ticket SSE pattern exactly (initial snapshot, full refetch on every `QueueEventsService` change, heartbeat), but publishes a `DisplaySnapshot` (tenant/location/queue name+status, `nowServing: [{ticketNumber, serviceName}]`, `next: number[]`) that is **structurally incapable of carrying customer or staff identity** — the underlying Prisma queries never select those fields in the first place (defense in depth, not just an omitted DTO field). - **Real bug found and fixed while building this**: `QueuesService.updateStatus()` (pause/close) never called `QueueEventsService.emitQueueChanged()` — pausing or closing a queue was invisible to every SSE watcher (both the Phase 4 ticket page and this phase's display) until their next unrelated update or a manual refresh. Fixed by emitting on every status change; caught by the Playwright verification run (pause didn't show up on the board), not by any pre-existing test — a new unit test now covers it.
- `apps/web/src/app/display/[code]`: fullscreen, dark board — large "Now Serving" ticket numbers + service name (one per currently-CALLED/SERVING entry, so `servingCapacity > 1` shows multiple), a "Next Up" row, and a paused/closed message when the queue isn't accepting. `EventSource` auto-reconnects on a clean drop; a 70s watchdog force-reconnects on a silently-stalled connection (a TV left running for hours needs this more than a customer's own ticket page does). `/display` itself is just a guidance page — no display-picker UI exists (see Known Issues).

### Phase 7 — Notification Infrastructure

- **Outbox pattern (ADR-008/G-31)**: new `NotificationOutbox` model (`tenantId`, `queueEntryId`, `type`, `channel`, `recipient`, finalized `body`, `status: PENDING|SENT`). `NotificationsService.enqueue(tx, ...)` writes a row inside the caller's own transaction; `processPending()` claims each row via a guarded `PENDING→SENT` update _before_ calling the provider (only the caller whose update actually matched proceeds to send — the exactly-once-delivery guarantee), reverting to `PENDING` on a provider failure so a later pass retries. Every mutation triggers processing fire-and-forget (`triggerNotificationProcessing()`, never awaited) — a queue operation's HTTP response never waits on it.
- **`NotificationProvider`/`MockNotificationProvider`** (`apps/api/src/notifications`): same abstract-class-as-DI-token pattern as `MailService`/`ConsoleMailService`, but a distinct interface/module (SMS-first, queue-event shaped) — logs instead of sending, plus an in-memory `sent[]` log for test introspection.
- **G-31 threshold engine**: `Queue` gained `approachingThreshold`/`nearlyNextThreshold` (people-ahead, configurable, defaults 5/2); `QueueEntry` gained `approachingNotifiedAt`/`nearlyNextNotifiedAt`/`calledNotifiedAt` (timestamps double as the "already sent" gate and an audit trail). `evaluateWaitingThresholds` re-scans every WAITING entry's position (list order = position) after every mutation that could shift it (join, call-next, any staff transition), enqueuing `APPROACHING`/`NEARLY_NEXT` the first time each is crossed — checked nearest-first, so jumping straight into a nearer tier suppresses the further one (stamped as sent, never actually fired). `CALLED` fires once from `callNext`, suppressing any still-unfired lower tier for that same entry. `RECALLED` fires unconditionally on every staff-triggered recall (never gated — a deliberate resend, not a threshold).
- **Real concurrency bug found and fixed while building this**: `evaluateWaitingThresholds`'s row updates could deadlock against a _different_ simultaneous Call Next on the same queue — two staff calling next at once could each lock a different WAITING row (ADR-006's own `SKIP LOCKED` design), then each try to update the row the _other_ transaction held, a classic circular wait. Caught by the pre-existing Phase 3 concurrency integration test (8 simultaneous joins + 12 simultaneous Call Next), not a new one. Fixed by claiming only the specific rows about to be written via the same `FOR UPDATE SKIP LOCKED` pattern first — a row locked elsewhere is simply skipped this pass (its notification fires on the queue's next mutation instead); verified deadlock-free across multiple repeated runs of the concurrency test after the fix.
- Tests: 7 new unit (`notifications.service.spec.ts`, `mock-notification.provider.spec.ts`) + 4 new queue-entries unit tests (threshold firing/suppression/RECALLED) + 1 new queues unit test → 125 total unit; new `notifications.integration-spec.ts` (6 tests: the full vertical slice with exactly one CALLED notification, threshold suppression, cross-entry cascade after a call, unconditional RECALLED, duplicate-processing-never-duplicates, provider-outage-doesn't-block-the-mutation) → 40 total integration. `pnpm quality` green end to end.
- Manual verification: a real queue driven via curl end to end with tight thresholds — join 3 customers (NEARLY_NEXT/NEARLY_NEXT/APPROACHING fired correctly by position), call-next (CALLED fires, and the newly-promoted 3rd customer correctly gets NEARLY_NEXT in the same pass), recall (RECALLED fires) — cross-checked against both the mock provider's log output and the `notification_outbox`/`queue_entries` tables directly via `psql` (exact 1:1 row-to-log-line match, every row `SENT`, every suppression flag correctly stamped).
- **This completes the plan's original first vertical slice** (§98/C-03): scan → join → position updates → staff calls → customer notified (mock) → complete — proven end to end by the integration test of the same name.

- **Mid-phase user request: split Email and SMS into independently swappable providers** (rather than one `NotificationProvider` branching on channel) — implemented as the actual architecture, not just Pingram-specific. See ADR-008's updated Decision section for the full rationale.
- **`EmailProvider`/`SmsProvider`** (`apps/api/src/notifications`): two separate abstract-class DI tokens, each with its own config switch (`EMAIL_PROVIDER`/`SMS_PROVIDER`, in `apps/api/.env`). `notifications.module.ts`'s factory providers pick the implementation per switch and **throw a clear error at application startup** for any unrecognized value — a misconfiguration in production can never be mistaken for "it's actually sending." `MockEmailProvider`/`MockSmsProvider` replace Phase 7's single `MockNotificationProvider`.
- **`PingramEmailProvider`** — the real implementation: `POST https://api.pingram.io/email`, `Authorization: Bearer <PINGRAM_API_KEY>`, plain-text `body` wrapped as minimal escaped HTML for Pingram's `html` field, subject derived from `NotificationType` (`buildEmailSubject`). Never logs `PINGRAM_API_KEY` in any path, success or failure — only what Pingram's own response reports.
- **`SmsProvider` has no real implementation yet** — only `MockSmsProvider` exists; picking anything else for `SMS_PROVIDER` throws at boot (matches the roadmap's explicit "SMS as a later adapter," G-29). Since every current queue notification is SMS-channel by construction (anonymous walk-ins only ever supply a phone, no email capture exists before Phase 9), turning on `EMAIL_PROVIDER=pingram` today wires up real email sending with no live queue traffic to actually exercise it yet — proven instead by a dedicated integration test that sets a customer's email directly in the DB (the same way Phase 9's real accounts eventually will) and confirms the CALLED notification routes to `EmailProvider`, not `SmsProvider`.
- Tests: 4 new unit (`mock-email.provider.spec.ts`, `mock-sms.provider.spec.ts`, `pingram-email.provider.spec.ts` — mocks `fetch`, asserts the Bearer header, HTML-escaping, and that a failure never logs the API key) + `notifications.service.spec.ts` updated for the two-provider split → 132 total unit; 1 new integration test (EMAIL-channel routing via a real Postgres customer record) → 41 total integration. `pnpm quality` green end to end.
- Manual verification: real dev-server boot with `SMS_PROVIDER=bogus` fails loudly at startup with the exact intended error (proving no silent fallback); `EMAIL_PROVIDER=pingram` with no key boots cleanly (the check is deferred to send-time, not startup); a real join+call-next cycle against the mock providers confirmed `MockSmsProvider` (the renamed class) still fires identically to Phase 7's behavior.

## Known Issues

- **G-40 partial**: Cloudflare Turnstile (the specific bot-check the plan calls for on the join POST) is not integrated — only IP-based rate limiting (`@nestjs/throttler`, 5/min on join) ships. Adding Turnstile requires an external Cloudflare account/site key.
- **Real Pingram email not yet live-verified** — `PingramEmailProvider` is fully built and tested (mocked `fetch`), but nobody has set a real `PINGRAM_API_KEY` yet. `EMAIL_PROVIDER` stays `mock` until that exists. Auth OTP/invite emails are unrelated — `MailService` is still `ConsoleMailService` (Phase 1, never in scope for Phase 8's `NotificationProvider`-based queue notifications).
- Real SMS provider not integrated at all (not just unverified) — only `MockSmsProvider` exists; `SMS_PROVIDER=pingram` (or anything but `mock`) throws at boot by design. Deliberately deferred (G-29) until real per-tenant cost caps exist.
- Network-level rate limiting (G-38, Redis/Upstash-backed, for horizontal-scale/multi-instance deployments) not yet wired — deferred to Phase 12 as scoped. Current rate limiting is in-process only, correct for the current single-instance deployment (D-06).
- No background job/scheduler exists — business-hours-based auto-closing (as a fallback to staff-controlled closing, G-16) and auto-no-show-after-grace-period (G-15) are both designed but not implemented; staff must act manually for now.
- SSE realtime is in-process (`EventEmitter`) only — correct for single-instance (D-06), but will need a Redis pub/sub swap before horizontal scaling or the future high-volume "flash crowd" workstream (see `docs/roadmap.md`'s future-enhancements section).
- Testcontainers' Ryuk reaper sidecar hangs in this sandboxed Docker dev environment; `apps/api`'s `test:integration` script sets `TESTCONTAINERS_RYUK_DISABLED=true` to work around it (see `test/jest-integration.config.js` for the full explanation). Not an application bug — purely an environment quirk of this Docker setup.
- The staff dashboard polls every 3s rather than using SSE — deliberate for MVP simplicity (EventSource can't attach an Authorization header, and a query-string token is a security smell not worth taking on this phase); fine at current staff-tablet counts, worth revisiting if multi-tablet live sync becomes a real complaint.
- No staff-facing UI yet for creating/managing locations, services, queues, or codes (including display codes) — Phase 5/6's work assumes these already exist (created via curl/API in this session's manual testing). A business-admin UI for this is not yet scoped into any phase; flag to the user if it's wanted before Phase 11 (Business Administration).
- No display-picker UI — a business owner points the TV's browser at the specific `/display/{code}` URL directly (bookmarked once). Fine for one screen per location (D-10); would need a picker if a business ever wants several distinct boards.
- Notification processing is fire-and-forget in-process, not a real background worker/queue — correct for MVP scale (ADR-008 describes "a background worker sends it," which this satisfies in spirit: never blocks the request), but a genuinely down/slow provider only gets retried on the _next_ queue mutation to the same entry, not on a timer. Revisit once Phase 8's real provider makes actual failures a real possibility, not just a simulated test.
- No staff-facing UI to configure `approachingThreshold`/`nearlyNextThreshold` per queue — set via `PATCH /tenants/me/queues/:id` today (already wired through), no dashboard control for it yet. Same "no business-admin UI" gap as other queue config (see above).
