# QueueFlow — Plan Review (Gaps, Contradictions, Pending Decisions)

**Date:** 2026-09-27
**Reviewed:** `docs/QueueFlow_Detailed_Plan.md` (3799 lines), `docs/QueueFlow_Visual_Prototype_and_Screen_Flows.md` (879 lines)
**Baseline compared against:** `/Users/m9rcy/dev/ai/budget-terry` (working web + Android app, NestJS/Prisma/Next.js/Expo)

## Verdict

The plan is unusually strong on **architecture posture** (modular monolith, tenant isolation, outbox, SSE-first, no-Kafka, no-microservices, concurrency-safe Call Next) and on **what not to do**. It is weak in three specific ways, and each will cost real session time if not fixed before Phase 0:

1. **It states principles where it needs formulas.** "Position is derived", "estimated wait = people ahead × average duration", "notify at 5 ahead" — none of these are specified precisely enough to implement without inventing rules mid-session. Inventing them mid-session means they get invented differently each session.
2. **Several named features have no data model.** Staff assignment on a queue entry, counters, ticket-number allocation, requeue/parked state, tenant signup, staff invitation. The dashboards and displays in the visual doc require fields the schema doesn't list.
3. **MVP scope is roughly 3–5× what it should be** for solo, session-bounded (5h) AI-assisted development. It contains everything except billing.

Everything below is tagged with an ID so `PROJECT_STATUS.md` can track resolution.

## 4.5 New subsystem: Customer Identity & Self-Serve Check-In

Designed in discussion 2026-09-27. This **replaces the plan's QR-Context-Platform framing with a wider one**, not a second bolted-on system: a code is a pointer, and what it holds determines what happens — the type list just needed widening to cover people and bookings, not only places and things.

**Unified `code` concept** (supersedes the plan's `qr_code` table description in §13.1):

```text
GENERAL, LOCATION, QUEUE, SERVICE, TABLE, APPOINTMENT, KIOSK, COUNTER   ← existing (place/business-owned)
CUSTOMER_IDENTITY                                                       ← new (customer-owned, persistent)
GUEST_CARD                                                              ← new (location-owned, numbered pool, anonymous, recycled)
APPOINTMENT_TICKET                                                      ← new (appointment-owned, one per booking)
PRODUCT, PAYMENT                                                        ← future, unchanged
```

One resolver (`code → resolve → {type, owner, payload}`); the scanning app branches on `type`. A customer's phone scanning `QUEUE` shows join/book options (unchanged from the original design). A kiosk scanning `CUSTOMER_IDENTITY` or `GUEST_CARD` self-serve-joins the queue it's bound to. A kiosk scanning `APPOINTMENT_TICKET` checks that specific booking in. Storage can carry `owner_type`/`owner_id` (tenant vs customer vs guest-card slot vs appointment) alongside the existing `context_type`/`context_id`, rather than forking into a second table/resolver — lifecycle rules (who creates it, rotation, expiry) still differ per kind at the service layer, but that's normal branching, not an architectural fork.

Two things explicitly do **not** need a new type — they're just new uses of what already exists:

- **A guest's ticket shown as a QR** on the confirmation page is the existing `queue_entry.public_token` link, rendered as an image as well as a tappable link. Same resolution endpoint. Partly fixes G-45 (ticket recovery) for free — a saved/screenshotted QR survives even if the SMS is lost.
- **A dedicated "sign up here" poster** is just a `LOCATION`/`GENERAL` context configured with a different capability set (`CREATE_ACCOUNT` instead of `JOIN_QUEUE`/`BOOK_APPOINTMENT`) — same table, same resolver, different poster.

**Guest card mechanics (corrected from an earlier oversimplification in this review — numbered + idempotent requires tracking, a generic shared code does not):**

- Each numbered slot (`guest_card`: id, tenant_id, location_id, stable code value, currently-linked `queue_entry_id` or null) tracks whether it's currently in use.
- **Scan is idempotent**: if the slot already has an active (non-terminal) queue entry, re-scanning does not create a duplicate — it just re-displays that entry's current status on the kiosk screen.
- **Auto-release, no manual "return" step in software**: once the linked queue entry reaches a terminal state (completed/cancelled/no-show), the slot becomes available for the next scan automatically. Physically returning the card to the rack is a staff housekeeping process, decoupled from this — a card that doesn't make it back causes no data problem, only an inventory one.
- **No self-service cancellation path** for a guest-card user (there's no phone/account to authenticate a self-cancel through) — someone who needs to leave early must ask staff to cancel their entry from the existing staff dashboard action (§28). No new capability needed; just note it as the only path for this user type.
- The earlier "someone could re-scan one card repeatedly to farm tickets" concern is resolved by idempotency itself (a re-scan of the _same_ card never creates a second entry); scanning multiple _different_ numbered cards for a group is normal, intended use, inherently bounded by the pool size.

## 7. Stack recommendation (D-01) in detail

**Recommend NestJS + Prisma + PostgreSQL + Next.js, pnpm workspaces — i.e. budget-terry's stack.**

Why, specific to this project and this constraint:

- **Session economy.** A 5-hour budget punishes context switching. One language means one mental model, one test runner story per layer, and shared `packages/types` + `packages/validation` (Zod) so a DTO change can't drift between API and web. In a Java+TS split, every contract change is two files in two languages plus a mapping layer.
- **Direct reuse, not inspiration.** Copyable today from budget-terry: the OTP login-code flow (`LoginCode` model, `TokenService.generateLoginCode/hashLoginCode`, attempt counting, generic failure responses), refresh-token rotation (ADR-011), the trusted-device plan, the global `JwtAuthGuard` + `@Public()` opt-out (protected-by-default, exactly right for a multi-tenant app), `ZodValidationPipe`, Testcontainers integration harness, `pnpm quality`, `scripts/dev.sh`, CI, Resend mail service.
- **SSE is first-class in Nest** (`@Sse()` + rxjs), and a long-lived container is a better SSE host than a serverless function.
- **The one real trade-off:** Prisma has no first-class `FOR UPDATE SKIP LOCKED`. That's one `$queryRaw` in the Call Next path (G-20) and one in ticket-number allocation (G-10) — bounded, testable, and documented in an ADR. If that offends, Drizzle or Kysely express it natively; that's a smaller decision than changing language.
- **Where Spring genuinely wins** — mature JPA optimistic locking, `@Transactional` semantics, a stronger story if this ever becomes a large team's enterprise product. If long-term enterprise positioning matters more than shipping the pilot, that's the argument for Spring. It is not the argument for the next six months.

**Frontend:** keep **Next.js** — SSR of the QR landing page is genuinely valuable (a customer scanning a wall poster on mobile data wants first paint fast, and the context resolve is a server fetch). Two deployment caveats: (a) if web is on Vercel and API elsewhere, `EventSource` is cross-origin — CORS plus no custom headers on `EventSource`, so the ticket token must travel in the URL path, which it already does; (b) consider serving Next from the same container/origin as the API to avoid that entirely.

**Keep the `apps/` + `packages/` split even though there's no native app yet** — it's the cheap thing that makes "add Expo later" a new app rather than a refactor, and budget-terry already proves the layout works.

**One inherited trap to avoid:** budget-terry lost three phases to `ERR_MODULE_NOT_FOUND` because shared packages were ESM with extensionless imports while Nest runs CJS — passing `build`, `typecheck` and Jest the whole time without ever booting. Copy the _fix_ (compile shared packages as CommonJS) and the _rule_ (boot the real dev server at least once per phase) into `AGENTS.md` from day one.

## 9. The biggest single risk

The QR-Context-Platform framing (plan §4) is intellectually correct and strategically right — and it is also the most likely way this project dies. The plan already contains restaurant table ordering, menus, bills, payments, loyalty, forms, and a capability model, with diagrams, before one customer has joined one queue.

Mitigation, stated as a hard rule in `AGENTS.md`: **the QR layer in MVP is one table with `context_type` + a capabilities array, and one resolver endpoint.** No capability registry, no plugin abstraction, no ordering or payment tables, no `context_capability` join table. The generality lives in the _seam_ (a resolver returning capabilities, and capability modules owning their own logic) — not in infrastructure built for capabilities that don't exist. §13.3 says this already; it needs to be an enforced rule rather than a caveat.
